# Spec：MATT 模型灯光控制系统

> 状态：待实现（ready-for-agent）
> 范围：固件（ESP-IDF / ESP32-C3FH4）、微信小程序、NestJS + MySQL 后端、Vue + Element Plus 后台
> 相关设计记录：本 spec 的“Implementation Decisions”一节即决策来源，无需另行查阅。

## Problem Statement

我给自己拼装的高达、假面骑士模型内部焊了电路板，装了 LED 和 WS2812 灯带，分别做眼灯、胸灯、关节灯等。现在这套灯**只能通电就亮，没有任何控制手段**：

- 想改颜色或亮度就得改代码、重新烧录、再把外壳拆开重新装回去，一次调光等于一次拆机。
- 8 个输出引脚接的东西各不相同（有的是单颗 LED，有的是一条要分段的 WS2812 灯带），每换一个模型、改一次接线，固件里的引脚与灯型对应关系就得重写一遍。
- 我想要的效果不是“打开/关闭”，而是像“眼灯由暗红渐变到亮红、0.5 秒后胸灯开始呼吸蓝、循环”这种带时间轴的编排，靠改几行代码根本表达不出来。
- 一个人往往有好几个模型，每个模型的接线和灯效都不一样；出去玩的时候想用手机现场切换效果，不可能背一台笔记本。

所以问题是：**我需要一个能用手机现场控制的、支持时间轴灯效编排的、接线可配置的模型灯光控制系统，而且配置和灯效要能在设备上持久保存，手机不在也能正常亮。**

## Solution

一套四件的系统：**手机上的微信小程序**通过蓝牙直连模型里的 ESP32-C3 控制板，完成扫描、连接、实时调光调色；**灯效编排器**放在小程序里（因为实时预览必须依赖蓝牙连接）；**NestJS + MySQL 后端**作为配置中心，只存设备档案、用户归属、场景二进制和固件版本，不参与任何实时控制；**Vue + Element Plus 后台**用于管理用户与设备、维护场景模板库、管理固件版本。

控制板上电后即按**上一次保存的场景**自动播放，不需要手机在场。用户在小程序里编排好一条场景（每个通道一条时间序列、每条 WS2812 灯带再分段、每段的每一帧由一个背景层加一个灯效层混合而成），通过蓝牙分片下发并写入 Flash，之后即使手机断连、关机、离开，模型仍按这条场景循环播放。

接线方式通过配置下发：8 个通道接哪个引脚、是 WS2812 还是普通 LED、灯带多少颗灯珠、怎么分段，全部由小程序写入控制板并持久化，换接法不需要重新烧录固件。

## User Stories

### 连接与配对

1. 作为模型主人，我想在小程序里看到附近所有 `MATT-` 前缀的控制板列表，以便快速找到我要控制的那个模型。
2. 作为模型主人，我想在设备列表里直接看到每台设备的蓝牙信号强度，以便在多个模型同时通电时判断哪个离我最近。
3. 作为有多台设备的用户，我想给每台设备起一个我认得出来的名字（如“牛高达”“W 骑士”），以便不靠 MAC 地址区分设备。
4. 作为模型主人，我想在连接成功后立刻看到 8 个通道的当前状态（亮/灭、颜色、亮度），以便知道模型现在是什么样子。
5. 作为模型主人，我想在小程序首页一键重连“上一次连接的设备”，以便省掉每次扫描的等待时间。
6. 作为模型主人，我想在连接过程中看到明确的进度提示（扫描中 / 连接中 / 已连接 / 断连），以便知道当前能不能操作。
7. 作为模型主人，我想在小程序切到后台后重新打开时被提示“连接已断开，需重新连接”，以便不被静默的失效连接误导。
8. 作为模型主人，我想在第一次连接一台新设备时完成一次配对，把设备绑定到我的账号，以便别人不能随手连上改我的灯效。
9. 作为模型主人，我想在设备被别人误绑、或我自己换手机后，通过长按板子上的 BOOT 键 5 秒恢复出厂，以便不用拆开模型外壳就能重新绑定。
10. 作为模型主人，我想在恢复出厂时得到“配置和绑定 token 都被清除”的明确结果，以便知道下一步应该重新配对和重新下发配置。

### 实时控制

11. 作为模型主人，我想单独打开或关闭任意一个通道，以便精确控制眼睛、胸口、关节等部位的亮灭。
12. 作为模型主人，我想给任意一个通道设置任意颜色，以便现场试出我喜欢的眼灯颜色。
13. 作为模型主人，我想用色盘而不是输入 RGB 数字来选颜色，以便在手机屏幕上直观地调色。
14. 作为模型主人，我想单独调任意一个通道的亮度，以便让胸灯比眼灯暗一些。
15. 作为模型主人，我想有一个全局亮度，一次性把整台模型调暗（比如夜里不想太刺眼），以便不用逐个通道去调。
16. 作为模型主人，我想一键全灭，以便在需要立刻关灯时不手忙脚乱逐个通道关。
17. 作为模型主人，我想在调整后立刻看到灯的变化（半秒内），以便调色时能实时看到结果。
18. 作为模型主人，我想在调节过程中即使误操作也能马上改回来，以便不担心把设备搞坏。
19. 作为模型主人，我想临时试播一个灯效（呼吸、流水、心跳等）而不保存，以便快速比对不同效果，不必先建场景。
20. 作为模型主人，我想在小程序里看到当前实际生效的通道状态，而不是只看到我自己刚才点过什么，以便确认指令真的生效了。
21. 作为模型主人，我想在小程序重新连上设备时自动同步设备的真实状态，以便界面和灯的实际情况一致。

### 通道与接线配置

22. 作为自己焊板子的用户，我想指定每个通道对应哪个 GPIO 引脚，以便接线改了不需要重新烧固件。
23. 作为自己焊板子的用户，我想指定每个通道是“普通单色 LED”还是“WS2812 灯带”，以便同一块板子驱动不同类型的灯。
24. 作为自己焊板子的用户，我想给每个 WS2812 通道填写灯珠数量，以便固件知道要刷新多少颗灯。
25. 作为自己焊板子的用户，我想把一条 WS2812 灯带划成若干段（最多 8 段），以便一条灯带上前 5 颗做左眼、后 5 颗做右眼。
26. 作为自己焊板子的用户，我想给每个通道和每段起名字（如“左眼”“胸口能量条”），以便编排时不用记住数字编号。
27. 作为自己焊板子的用户，我想在小程序里看到我配置的接线超出硬件能力时的明确报错（比如段数或灯珠数超限），以便知道该改哪里而不是灯莫名不亮。
28. 作为自己焊板子的用户，我想在控制板第一次使用时无需配置也能亮起来（编译期默认配置兜底），以便先确认硬件焊接没问题再去配细节。
29. 作为自己焊板子的用户，我想把一台设备已经调好的接线配置复制到同款模型的另一台设备上，以便不用重复配置一遍。
30. 作为自己焊板子的用户，我想把接线配置从设备读回来，以便换手机后不用凭记忆重填。

### 时间轴编排

31. 作为编排者，我想给每个通道单独编辑一条时间序列（最多 8 个关键帧），以便实现“眼灯先变红，一会儿再变蓝”。
32. 作为编排者，我想在关键帧里同时设置背景层（底色 + 透明度）和灯效层（效果类型 + 参数），以便同一时刻既有底色又有动画。
33. 作为编排者，我想调整每个关键帧的时间点，以便控制效果变化发生的节奏。
34. 作为编排者，我想在相邻关键帧之间自动平滑过渡（线性颜色插值），以便不会出现生硬跳变。
35. 作为编排者，我想给每条序列选择“循环播放”或“播放一次就停”，以便“呼吸”可以一直循环而“开机闪一下”只播一次。
36. 作为编排者，我想让所有通道的时间序列共享同一个全局时钟，以便“眼灯亮后 0.5 秒胸灯亮”这样的编排不会慢慢漂移。
37. 作为编排者，我想给一条 WS2812 灯带的不同段分别设置时间序列，以便眼睛和胸口的灯带能各自独立变换。
38. 作为编排者，我想通过透明度滑杆控制灯效层与背景层的混合比例，以便灯效不会完全盖掉底色，做出更细腻的效果。
39. 作为编排者，我想在编排界面上直接预览当前场景在模型上的实际效果（通过蓝牙实时下发），以便不靠想象调效果。
40. 作为编排者，我想暂停和继续预览，以便定格看清某一帧的样子。
41. 作为编排者，我想在预览时单步跳到一个关键帧，以便精确检查这一帧的参数。
42. 作为编排者，我想保存编辑好的场景并取个名字，以便之后随时切回来。
43. 作为编排者，我想保存多个场景（最多 8 个存在设备上），以便“常态”“战斗模式”“待机”随时切换。
44. 作为编排者，我想在保存场景前知道它占多少空间、设备还剩多少空间，以便不会写到一半才发现存不下。
45. 作为编排者，我想在传输失败（蓝牙中断、校验不过）时得到明确报错并可以重试，以便不用重新编排一遍。
46. 作为编排者，我想在保存前先看到这个场景是否超出设备的资源限制（通道数、段数、帧数），以便知道要精简哪里。
47. 作为编排者，我想复制一个已有场景再修改，以便基于旧效果快速做一个新的。
48. 作为编排者，我想删除不再需要的场景，以便腾出空间。
49. 作为编排者，我想在切换场景后模型立刻开始播放新场景，以便现场表演时快速换效果。

### 灯效种类

50. 作为编排者，我想用“常亮”效果给一个通道设一个固定颜色，以便做最简单的亮灯。
51. 作为编排者，我想用“呼吸”效果并设置周期和最小亮度，以便做像呼吸一样的明暗起伏。
52. 作为编排者，我想用“闪烁”效果并设置周期和占空比，以便做警示灯或故障灯的效果。
53. 作为编排者，我想用“流水”效果并设置速度和拖尾长度，以便做能量条从左到右填满的效果。
54. 作为编排者，我想用“彩虹”效果并设置速度和色相偏移，以便做七彩流转的底座灯。
55. 作为编排者，我想用“渐变”效果并设置两个颜色和周期，以便让灯光在红和蓝之间来回过渡。
56. 作为编排者，我想用“闪电”效果并设置频率和强度，以便做战斗时能量爆发的效果。
57. 作为编排者，我想用“心跳”效果并设置周期和双跳间隔，以便做“咚-咚”两下的生命体征效果。
58. 作为编排者，我想给流水、彩虹、渐变设置正向或反向，以便改变流动或过渡的方向。
59. 作为编排者，我想在方向对某些效果（呼吸、闪烁、心跳、闪电）无意义时不会被强制要求填这个参数，以便界面不出现莫名其妙的必填项。
60. 作为编排者，我想每种效果的参数有一个合理的上下限约束（比如周期最短 200ms），以便不会误填出固件处理不了的数值。
61. 作为编排者，我想在参数里设置灯效层的主色（渐变效果则有两个颜色），以便同一个效果能配出任意的配色。

### 持久化与开机

62. 作为模型主人，我想控制板上电后自动播放上一次使用的场景，以便不用掏出手机就能亮。
63. 作为模型主人，我想控制板上电后先稍等一小会儿再亮（软启动），以便避免通电瞬间电流冲击。
64. 作为模型主人，我想全局亮度独立保存在设备上，以便开机时的亮度就是我上次调好的。
65. 作为模型主人，我想在手机不连接、甚至不在场的情况下模型也照常播放场景，以便把它当摆件长期展示。
66. 作为模型主人，我想停机断电后配置和场景都不会丢，以便不用每次重新配置。

### 固件升级

67. 作为模型主人，我想通过小程序蓝牙给控制板升级固件，以便不用拆开模型外壳接线烧录。

69. 作为模型主人，我想在升级失败（断电、中断）时设备仍能回到旧固件正常开机，以便不会变砖。
70. 作为模型主人，我想在设备信息里看到当前固件版本，以便知道要不要升级。
71. 作为后台管理员，我想上传新的固件文件并登记版本号和说明，以便给设备下发。

## Implementation Decisions

### 系统边界与总体架构

四个独立交付物，边界严格如下：

- **固件**（ESP-IDF，C）：ESP32-C3FH4。负责开关灯、驱动 WS2812 与 PWM、场景播放、NVS 持久化、BLE 服务端。
- **微信小程序**（原生 + WXML/WXSS）：唯一的实时控制端，同时是编排器。
- **后端**（NestJS + TypeORM + MySQL）：配置中心。**绝不参与实时控制链路**，只存档案与二进制配置。
- **后台**（Vue 3 + Element Plus）：管理与只读查看，不做编排。

关键架构决策：**没有 WiFi、没有 MQTT、没有 WebSocket 实时链路**。所有实时控制走 BLE 直连。后端只在“用户打开小程序、需要拉取/上传配置”时被调用。

### 通道模型

- 通道数固定上限 **8**，索引 0–7。
- 每个通道有一个类型：普通 LED（单色，走 PWM 调光）或 WS2812 灯带。
- **8 个通道都允许配成 WS2812**，包括同一时刻只可能有一条在刷新的情况（见驱动决策）。
- 每个通道有：引脚、类型、灯珠数（WS2812 有效）、名称、亮度、开关状态。
- WS2812 通道可划分 **最多 8 个段**，每段有起始灯珠索引、灯珠数、名称。

### 驱动决策（关键，且是一个被接受的妥协）

- **所有 WS2812 通道都走 RMT，软件串行轮转刷新**。ESP32-C3 只有 2 个 RMT TX 通道，无法 8 路并行；因此固件在同一个渲染周期内依次刷新各条灯带，而不是同时。
- 代价：每条灯带的实际刷新率随灯带数量与灯珠数下降。接受这一代价，并**在固件中给每条灯带灯珠数设上限**（初值 32）以保证轮转刷新率不低于可用阈值。
- 普通 LED 走 LEDC（C3 只有 6 个 LEDC 通道），超出部分由软件 PWM 承担。具体分配策略在实现时确定，但**对上层必须表现为统一的“通道亮度”接口**。
- 通道类型、引脚、段划分全部来自 NVS 配置，**不是编译期常量**；编译期只提供一份出厂默认配置，用于 NVS 为空时的兜底。

### 引脚分配

- 通道引脚可配置，出厂默认映射：通道 1–8 → GPIO 0, 1, 3, 4, 5, 6, 7, 10。
- 保留 **GPIO 9（BOOT 键）** 用于长按 5 秒恢复出厂。
- 必须避开：GPIO 2/8/9（strapping）、GPIO 18/19（USB）、GPIO 20/21（UART0）。固件在写入配置时要拒绝这些引脚。

### BLE 服务

单一自定义 GATT 服务下的若干特征，UUID 全部固定，**所有设备共用一套 UUID，靠广播名区分设备**。

- 广播名：`MATT-` + MAC 末 4 位十六进制。
- 广播的厂商自定义数据中只放 **DeviceID 的前 4 字节摘要**（因为 iOS 拿不到真实 MAC，且广播包只有 31 字节）。
- 完整 DeviceID 是一个 16 字节 UUID，首次配对时由小程序生成并写入固件 NVS。**DeviceID 是后端记录设备的唯一键。**
- 特征划分见下节。

### 双通路的协议设计（核心）

BLE 上存在**两条语义完全不同的通路**，这是整个协议设计的中心思想：

1. **即时控制通路**：小包、无需应答、Write Without Response、目标低延迟。用于开关、颜色、亮度、临时试播、播放场景。
2. **配置同步通路**：大包、分片、带 CRC 与 ACK、可重试。用于场景、通道/接线配置、固件包。

另外必须有**状态读回通路**（Read + Notify），因为即时指令是无状态的：小程序退出再进来时，必须能问设备“你现在是什么状态”，否则界面和实际灯效会不一致。这是被明确采纳的要求，不是可选项。

OTA 使用**独立的特征对**（写入 + ACK 通知），不复用配置同步通路，避免固件包与配置包相互干扰，也让小程序端能单独呈现进度。

### 即时指令集

指令为 `[op][ch][载荷...]` 形式，控制在单包 20 字节以内以适配最差 MTU。操作包括：

- 设置通道颜色（RGB + 透明度）
- 设置通道亮度
- 通道开关
- 设置全局亮度（用特殊通道值表示“非通道操作”）
- 播放某个场景
- 全灭
- 临时试播一个灯效（效果 ID + 定长参数区），不写 Flash

### 状态读回

状态帧包含：协议版本、全局亮度、当前场景索引、通道数量，然后逐通道给出类型、亮度、开关、当前主色。读回长度会超过 20 字节，因此小程序连接后要主动请求更大的 MTU，并对分片读回做拼装。

### 分片传输协议

配置同步与 OTA 的分片格式一致：

- 每片带包序号、目标缓冲区偏移、数据。
- 接收方在收齐一个完整对象后校验 CRC16，再回 ACK（序号、状态码、CRC）。
- 状态码至少区分：成功、CRC 错误、空间不足、非法请求。
- 单包有效载荷随协商后的 MTU 自适应。

### 配置对象格式

配置对象带类型标识（通道/接线配置、场景、引脚映射），每个对象头部带长度与 CRC。

**场景对象承载三层嵌套结构**：

```
场景
 └─ 通道 (1..8)
     ├─ 通道级时间序列（≤8 关键帧）
     │    └─ 每帧：时间点 + 背景层 + 灯效层
     └─ 若为 WS2812：段 (1..8)
          └─ 段级时间序列（≤8 关键帧）
               └─ 每帧：时间点 + 背景层 + 灯效层
```

- 每个时间序列有自己的“循环/单次”标志与总时长。
- 背景层：一个基色 + 透明度。
- 灯效层：**定长 12 字节参数区**，包含效果 ID、方向位、透明度、两个 16 位参数、主色、副色。

采用定长参数区的原因：固件与小程序都能用同一套解析逻辑处理全部效果，不需要为每种效果写分支；后台表单也能统一渲染。**方向位对所有效果都存在，但对呼吸/闪烁/心跳/闪电等无方向语义的效果被忽略但仍占位。**

### 图层合成规则

最终颜色按透明度混合：`result = 背景色 × (1 − alpha) + 灯效色 × alpha`。

灯效层**铺满整段**，不做“段内局部范围”。这是有意识的范围收缩：一旦引入局部范围，段内边界计算与插值复杂度显著上升。

### 时间与插值语义

- 时间单位毫秒。
- 关键帧之间做**线性 RGB 插值**（不做色相插值，避免计算开销与实现分歧）。
- 所有通道与段的时间序列**共享同一个全局时钟**，避免多通道编排漂移。

### 容量与持久化决策

- 规模上限：**8 通道 × 每通道 8 段 × 每段 8 关键帧**。
- 场景须能存进设备 Flash 并在上电时自动播放；运行时只把**当前场景**载入 RAM，其余场景留在 Flash 中按需读取（C3FH4 只有 400KB SRAM）。
- 全局亮度独立持久化。
- 上电行为：**播放上一次使用的场景** + 约 200ms 软启动延时 + 应用持久化的全局亮度。
- 当存储空间不足时，固件必须**拒绝写入并回报明确错误**，而不是静默截断。

### 配对与安全

- 首次配对时小程序生成 16 字节 DeviceID 与配对 token，写入固件 NVS；此后每次连接写入 token 做校验。
- 换绑/失联的救援路径：**长按 BOOT 键 5 秒清除 token 与配置，回到出厂状态**。这是必须实现的，否则只能拆壳。
- 明确接受的安全边界：这是非商用、小团队场景，不做加密配对、不做防中间人。

### 设备唯一标识

用 **DeviceID（16 字节 UUID，存于 NVS）**，而不是 MAC 地址，因为 iOS 上小程序拿不到真实 MAC。

### 后端数据库

核心表：用户、设备（含 DeviceID、归属用户、模型名、固件版本、最后在线时间）、设备配置档案（通道与引脚映射）、场景、固件、设备固件升级记录、绑定 token。

**关键决策：场景在后端以原始二进制 payload 存储**（即分片拼好后直接下发给固件的那份字节），后端**不解析、不重新序列化**。理由是场景格式仍在迭代，后端跟随会成为持续负担；代价是后台无法展示场景内部细节，只能展示名称、大小、校验和。这是有意识的取舍。

### API 契约要点

后端只提供配置中心类接口，大致分为：微信登录换 token、用户信息、设备的增删改查与绑定/解绑、设备配置档案读写、场景的创建/读取/删除/批量应用、固件上传与版本管理、升级记录查询、绑定 token 签发。所有接口要求登录态，用户只能访问自己名下的设备与场景（管理员除外）。

### 编排器的位置

**编排器只在小程序里**。理由：实时预览必须依赖 BLE 连接，放在后台就必须在两端各写一套编排器并保持格式一致，工作量翻倍且极易发散。后台因此**只做只读查看 + 模板库 + 批量应用 + 用户/设备/固件管理**。

### 测试 seam（已与用户确认）

三个 seam，覆盖全部可自动化测试的逻辑：

1. **固件：平台无关的纯函数库**。把协议编解码与场景/灯效合成抽成不依赖 ESP-IDF 的 C 代码，在主机上用 Unity 做单元测试。BLE、RMT、NVS、按键只做薄封装，靠硬件人工验证。
2. **小程序：`BleTransport` 接口**。页面与编排器只依赖该接口，测试用 mock transport 注入，无需真机。
3. **后端：HTTP 层 supertest + repository 接口打桩**。场景 payload 只做二进制透传，用固定 fixture 字节串验证往返一致。

### 交付顺序

按“能立刻看到灯亮”排序，而不是按模块：

1. 固件最小可跑：BLE GATT 骨架 + 8 通道驱动 + 直接设色 → 用通用 BLE 调试工具点亮。
2. 固件协议层完整：即时指令 + 状态读回 + 配置同步分片。
3. 小程序控制页：扫描/连接/色盘/亮度/开关。
4. 固件场景引擎：时间序列 + 段 + 双图层 + NVS 持久化。
5. 小程序编排器。
6. 后端。
7. Vue 后台。
8. OTA over BLE。

## Testing Decisions

### 什么算好的测试

只测试**外部可观察的行为**，不测试实现细节：

- 对固件纯函数库：给定一段字节流，断言解析出的结构；给定场景 + 时间点，断言合成出的像素颜色。**不**断言内部用了哪个缓冲区、遍历顺序如何。
- 对小程序：给定 mock transport 的状态流，断言页面呈现的数据与发出的指令序列。**不**断言 WXML 结构细节。
- 对后端：给定 HTTP 请求，断言响应与数据库副作用。**不**断言 TypeORM 的查询写法。

不使用依赖真实硬件的自动化测试；硬件行为靠人工按清单验证。

### 将被测试的模块

1. **固件协议编解码**（纯 C，主机可跑）
   - 即时指令解析：合法/非法指令、越界通道值、超长载荷。
   - 状态帧编码：字段布局与总长度。
   - 分片重组：乱序、丢包、重复包、CRC 错误、偏移越界、超出容量时返回“空间不足”。
   - 场景对象反序列化：三层嵌套结构、帧数/段数越界、定长参数区长度校验。
2. **固件场景与灯效合成**（纯 C，主机可跑）
   - 线性插值：关键帧中间时刻的颜色计算。
   - 循环与单次两种序列结束行为。
   - 双图层透明度混合的边界值（alpha=0、100）。
   - 8 种灯效在若干时间点的输出；方向位对流水/彩虹/渐变生效、对呼吸/闪烁被忽略。
   - 参数钳制：超出上下限的周期、速度、占空比被夹到合法区间。
   - 分段映射：段的灯珠索引到灯带缓冲区的正确映射，段区间不重叠不越界。
3. **小程序 BLE 传输层**（mock transport）
   - 扫描过滤（只出 `MATT-` 前缀）、连接状态机、断连重连、MTU 协商失败后的降级分包。
   - 指令序列化与状态帧拼装。
4. **小程序编排器状态**（纯逻辑层）
   - 场景数据结构的新增/删除/拖拽关键帧、段划分合法性校验、容量估算与超限提示。
5. **后端**
   - 鉴权与设备归属隔离：用户 A 无法读写用户 B 的设备与场景。
   - 场景 payload 二进制透传往返一致。
   - 固件上传的版本号唯一性与校验和。
   - 批量应用场景模板到多台设备的部分失败处理。

### 先例（prior art）

仓库当前为空，**没有既有测试可参考**。因此本 spec 同时确立了各类测试的基准形态：

- 固件：Unity 断言风格的主机端测试，每个 seam 一个测试可执行文件。
- 小程序：Jest + 手写 `BleTransport` mock。
- 后端：NestJS 默认的 Jest + supertest 端到端测试。

## Out of Scope

- **WiFi / MQTT / 云控**：明确不做。设备不联网，不参与任何远程控制。
- **功率限制 / 电流保护**：不做自动亮度压降。用户自行在测试时由小功率逐步加大。固件不承担电源保护职责。
- **其他外设**：舵机、步进电机、传感器、红外、音频、屏幕一律不做，第一版只做灯光。
- **灯效层的局部范围（段内起止位置）**：不实现，只做铺满整段。
- **深睡眠 / 低功耗管理**：不做，保证 BLE 始终可连。
- **加密配对 / 身份认证的安全加固**：非商用场景，明确接受较弱的安全边界。
- **后台的可视化编排器与场景内部结构展示**：后台只读且只到“名称/大小/校验和”粒度。
- **微信小程序之外的控制端**（App、网页控制台、语音助手等）。
- **固件签名验证 / 安全启动**。

## Further Notes

### 已知且被接受的现实限制

- 微信小程序在 iOS 上**无法在后台维持 BLE 连接**，切后台即断；Android 同样受限。产品设计上必须围绕这一点：首页做快捷重连、连接期间保持前台提示、重连后主动做状态同步。
- 每次连接都要扫描，天然有 1–3 秒等待。这是平台限制，不是可优化项。
- 部分 Android 机型 MTU 协商不稳定，实际单包可能只有 20 字节。协议必须能退化为小包分片。

### 容量估算

单个场景满配约 13KB，8 个场景约 100KB；固件侧 NVS 分区按 64KB 规划并采用压缩存储，同时必须在设计中处理“存不下”的显式错误路径。

### 需要在实现期确认的数值

以下数值在 spec 中只给方向，实现时定稿并同步到固件常量与小程序校验：

- 每条 WS2812 灯带的灯珠数上限（初值 32，用于保住轮转刷新率）。
- LEDC 与软件 PWM 的具体分配策略。
- 场景压缩算法。
- 各灯效参数的具体上下限（周期、速度、占空比、拖尾、双跳间隔等）。

### 词汇表

- **通道（Channel）**：一个可独立控制的灯光输出，最多 8 个，对应一个 GPIO。
- **段（Segment）**：一条 WS2812 灯带内部按灯珠索引划分的子区间，最多 8 段。
- **关键帧（Keyframe）**：时间序列上的一个时间点，携带背景层与灯效层参数。
- **背景层（Background layer）**：一个基色 + 透明度，铺满整个通道或段。
- **灯效层（Effect layer）**：一个带参数的动态效果，按透明度与背景层混合。
- **场景（Scene）**：一组通道/段的时间序列集合，可在设备上保存并播放，最多 8 个。
- **即时通路 / 配置通路**：BLE 上两条语义不同的指令通路。
